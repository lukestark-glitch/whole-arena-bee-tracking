# Decisions

Choices that are not obvious from the code, with the reason. Add an entry whenever a stage
makes such a choice. Do not rewrite old entries. If a decision changes, add a new entry
that replaces the old one and say so.

| ID | Date | Decision | Reason |
| --- | --- | --- | --- |
| D1 | 2026-11-13 | Simulator and tracker are separate programs that talk only over UDP. | The tracker must be testable against real hardware later without changes, and must not be able to read the ground truth. |
| D2 | 2026-11-13 | Messages are JSON, one object per UDP datagram. | Readable in a terminal and easy to debug. The data volume (about 1,000 small messages per second) does not need a binary format. |
| D3 | 2026-11-13 | Python with NumPy and SciPy for both programs. | The load is small (16 cameras × 20 bees × 60 Hz is about 19,000 points per second). Readability matters more than speed here. Slow parts can move to C++ after measuring. |
| D4 | 2026-11-13 | Both windows are browser pages with three.js, without a build step. | No installation, runs on a 2019 Intel MacBook, 3D and blur are built in. |
| D5 | 2026-11-13 | The tracking cameras are assumed to work in near infrared (850 nm). Colour detection is the documented alternative. | Independent of the film lighting. Detection is an exchangeable step: triangulation and tracking only receive points. |
| D6 | 2026-11-13 | Virtual cameras deliver points, not images. | The open question of the concept is triangulation, identity and hand-off, not image processing. Rendering 16 full-resolution streams would be slow and say little about reality. See Stage 8. |
| D7 | 2026-11-13 | Two cameras per camera node. | Halves the number of computers. The simulation models node delay and node failure accordingly. |
| D8 | 2026-11-13 | A 3D point needs at least three agreeing cameras, plus four further safeguards against ghost points. | Two cameras and two bees already produce two false intersections. Details in the concept paper, section 6.2. |
| D9 | 2026-11-13 | All timestamps are simulation time supplied by the simulator. | Pause, slow motion and repeatable runs. |
| D10 | 2026-11-13 | Nodes send raw pixel coordinates. The server applies the lens model and camera pose. | Calibration lives in one place and nodes stay interchangeable. |
| D11 | 2026-11-13 | Function reference is generated from docstrings with pdoc. `docs/code-map.md` is the hand-written overview. | A generated reference cannot fall behind the code. |
| D12 | 2026-11-13 | The robot is represented by `robot_emulator/`, separate from `simulator/` and `tracker/`. | Keeps clear which behaviour would belong to the existing robot's software. |
| D13 | 2026-11-13 | Equidistant fisheye model for the tracking cameras. | Lenses of 110° and more are not described well by the standard pinhole model with radial terms. |
| D14 | 2026-11-13 | `detections` and `truth` are split into several datagrams when they would reach 1400 bytes. Parts carry no part counter: every part repeats `frame`, `t` and the ids, and the receiver joins them. `target` and `robot_pose` are never split. | A part counter would add a field that is almost never needed (one datagram holds about 60 bees of one camera). A receiver cannot tell that a part is missing, which is the same as any other lost detection under UDP. |
| D15 | 2026-11-13 | Rounding for quantities the first protocol text did not cover: blob size 0.01 px; velocity, acceleration and `tilt_rad` 0.0001; `confidence` 0.01. | Matches the resolution of the neighbouring fields and keeps messages short. |
| D16 | 2026-11-13 | The field of view in the config is in radians (`fov_horizontal_rad: 1.919862` for 110°). | One unit for angles everywhere, as `CLAUDE.md` requires. The degree value is a comment next to it. |
| D17 | 2026-11-13 | Cameras sit exactly on the corners and long edges of the arena box, two per long edge at x = 0.30 m and 0.60 m. A node holds a corner camera and its neighbour on the same edge. | Simplest layout that matches Figure 3 of the concept paper. Offsets outside the acrylic are a question for Stage 7. |
| D18 | 2026-11-13 | The config holds only the four UDP ports. WebSocket ports are added in Stages 2 and 4. | Nothing is configured before something uses it. |
| D19 | 2026-11-13 | Flying bees follow a random velocity with damping (Ornstein-Uhlenbeck process) with a typical speed of 1 m/s and a direction memory of 0.5 s, capped at the maximum speed. They bounce off walls. | Gives smooth random turns with two readable parameters. A plain random walk of the velocity would drift to the 5 m/s cap and stay there. |
| D20 | 2026-11-13 | A flying bee lands only when it touches a wall (default chance 20 % per contact; lowered to 5 % in Stage 2 so that about half of the bees are in the air). Take-off, start and stop of walking happen at random with rates from the config. | A landing at a random moment in mid-air would teleport the bee to a wall, which no tracker should have to follow. |
| D21 | 2026-11-13 | Blob size = focal length × body length / distance, with a body length of 15 mm. | Small-angle size on an equidistant lens. Orientation of the bee is ignored. |
| D22 | 2026-11-13 | One node delay is drawn per node and frame (normal distribution, 8 ms mean, 2 ms standard deviation, never negative) and used for both cameras of the node. | Both images are processed by the same computer in the same frame time. |
| D23 | 2026-11-13 | All cameras must have the same frame rate; the config is rejected otherwise. The simulation step is one frame period. | One trigger source pulses every camera (concept paper, section 5.3). |
| D24 | 2026-11-13 | The UDP host `127.0.0.1` is a constant in `shared/protocol.py`, not a config value. | `docs/protocol.md` fixes the transport to localhost for the proof of concept. |
| D25 | 2026-11-13 | Stage 1 does not merge overlapping bees into one detection, although `docs/camera-node.md` lists that behaviour. | The Stage 1 plan does not ask for it. To be decided before Stage 3 baseline numbers are recorded. |
| D26 | 2026-11-13 | A camera does not report a bee that is closer than one body length, and a walking bee turns back at the edge of its wall. | Cameras sit on the arena corners and edges, where a bee at zero distance would get an infinite blob size. Turning back keeps the true velocity equal to the real motion. |
| D27 | 2026-11-13 | Replaces D25. Blobs that touch in a camera image (centre distance below half the sum of their sizes) are merged into one detection: area-weighted mean position, size with the same total area. | A real blob detector cannot separate touching bees. Without this the tracker's baseline would be too good. Requested by the user after Stage 1. |
| D28 | 2026-11-13 | The simulator serves its page and its WebSocket on the same port, using the HTTP hook of the `websockets` library. | One port, no second server and no extra dependency. |
| D29 | 2026-11-13 | Controls change the simulation only between frames. Removed bees are the newest ones, and a bee id is never used twice in a run. | Keeps runs repeatable and keeps the truth ids unambiguous for the metrics. |
| D30 | 2026-11-13 | While paused the simulator sends no UDP messages. A restart with a new seed starts again at frame 0 and time 0. | Simulation time stands still in a pause. Receivers must accept that time jumps back after a restart. |
| D31 | 2026-11-13 | three.js 0.160.0 is loaded from jsDelivr with a fixed version in the page. | Pinned CDN URL as `CLAUDE.md` requires; no build step. |
| D32 | 2026-11-13 | A track claims detections by the distance between its predicted point and the detection's ray (in metres), not by a pixel distance in the image. | The same step as "project and take the nearest detection", but one gate fits bees near and far from a camera, and the lens model is used only once (pixel to ray). |
| D33 | 2026-11-13 | A known track needs two agreeing cameras, a new point three; both also need half of the cameras that cover the place (`coverage_share`). | Two cameras keep a track alive in a poorly covered corner. The coverage rule stops a track from following the few rays that happen to run along its prediction error after a sharp turn; the bee is then found again as a new point and the track picks it up. This cut ID swaps in the baseline run from 47 to 9 per 20 s. |
| D34 | 2026-11-13 | Filter noise: jerk 1000 m/s³, measurement 2 mm; assignment gate 10 cm. | Tuned on the baseline run. The simulated bees change velocity abruptly, so a stiff filter (small jerk) lags and loses them; 300 m/s³ gave twice the position error. |
| D35 | 2026-11-13 | A track on probation is dropped after one frame without support. A confirmed track runs on prediction for up to 15 frames. | Ghost points rarely last five frames in a row; a real bee hidden for a quarter of a second should keep its ID. |
| D36 | 2026-11-13 | The receiver's timeout runs on the `t` of arriving messages. A frame is released incomplete when a message at least two frame periods newer arrives. | The tracker must not use the wall clock. If the cameras fall silent, the last incomplete frame waits, which changes no result. |
| D37 | 2026-11-13 | Metrics: a track matches a bee within 2 cm. An ID swap is counted whenever a bee is matched to another track ID than last time. A ghost track is unmatched in more than half of its frames. Only confirmed tracks count. | Simple definitions that can be checked by hand. A brief exchange of two IDs counts four swaps (two bees, there and back), so the number is a strict upper bound. |
| D38 | 2026-11-13 | Simulator, tracker and metrics end a run of duration D with the same last frame (the last one that starts before D). | All three stop by themselves with the same `--duration`, and the same frames are compared. |
| D39 | 2026-11-13 | The control window gets snapshots at most 30 times per second of simulation time, not wall time. | The tracker has no clock. In slow motion the window then updates more slowly, which matches what is happening. |
| D40 | 2026-11-13 | A node counts as stopped after 0.5 s of simulation time without a report from either camera. | Long enough to ignore single lost messages, short enough to show within the one second the plan asks for. |
| D41 | 2026-11-13 | A stopped node still draws its random delay in the simulator. | Stopping a node must not change the random numbers of the bees or of other nodes, so runs with and without the stop can be compared directly. |
| D42 | 2026-11-13 | The tracker treats frame numbers that jump back by more than 10 frames as a restart of the sender and drops all tracks. | The simulator window can restart the simulation. A late message is at most a few frames late (frames time out after two periods), so the two cases cannot be confused. A restart within the first 10 frames of a run is not noticed. |
| D43 | 2026-11-13 | The smoothed acceleration is computed in the tracker (exponential smoothing, 0.2 s), not in the page. | Pages hold no logic. The value will also go into the `target` message in Stage 5. |
| D44 | 2026-11-13 | A click selects the track nearest to the pointer on the screen (within 14 px), and rows of the track list can be clicked as well. | Bees are a few pixels large; exact hits on a moving sphere are hard. |
| D45 | 2026-11-13 | New module `shared/web.py` for serving a page next to a WebSocket. | Both windows need the same few lines, and `tracker/` must not import from `simulator/`. |
| D46 | 2026-11-13 | Robot parameters live in their own file `config/robot.yaml`, each with unit and source (`video`, `assumed`, `measured`). | The videos give sizes but no speed or acceleration limits. Real values from Jeremy Fielding can then replace the assumptions in one place, and the source shows which numbers are still guesses. |
| D47 | 2026-11-13 | Robot geometry: the rail runs along +x, the tilt axis is parallel to it, and at tilt 0 the cameras look along +y. The stereo camera shares the pose of the cinema camera and is modelled as one image with a measured distance per blob. | Rail, tilt and focus then cover x, z and y with no pan axis, as on the real robot. One image with distances is what the robot's software works with after rectification. |
| D48 | 2026-11-13 | The robot's stereo noise comes from a generator spawned from the simulation's one generator, not from that generator itself. | What the robot sees depends on when `target` arrives over UDP. With a shared stream that timing would change the bees. All randomness still comes from the one seed. |
| D49 | 2026-11-13 | `target.acc` carries the smoothed acceleration, and `others` lists at most 8 confirmed tracks inside the stereo image, each with `pos` and `vel`. | The raw filter acceleration is too noisy to extrapolate with. The robot extrapolates the target by one to two frames; without `vel` the other bees would be compared at an older time, up to a few centimetres off. Eight entries keep `target` in one datagram also with many bees. |
| D50 | 2026-11-13 | The tracker sends no `target` before the first `robot_pose`. | `distance_m` and `others` need the robot's pose; a guessed pose would send wrong values. |
| D51 | 2026-11-13 | Tracker option `--auto-select`: selects the oldest confirmed track whenever none is selected. | The 60 s measurement must run without a click in a window and repeat exactly. |
| D52 | 2026-11-13 | The track log gets a `selected` field per frame. | The metrics need to know which bee the robot was meant to follow; the log is the only tracker output they read. |
| D53 | 2026-11-13 | "In focus" means inside the cinema frame and within half the depth of field of the focus plane. | A sharp bee outside the picture is of no use, so the two numbers nest. |
| D54 | 2026-11-13 | Axes brake along the discrete braking curve (stopping from `n` steps of full deceleration takes `a·dt²·n(n+1)/2`), plus the target's velocity as feed-forward. | The continuous curve `sqrt(2·a·d)` overshoots at a finite control step and then breaks the acceleration limit. |
| D55 | 2026-11-13 | The selection rule looks only at the blob nearest to the prediction. If it fails the distance or the `others` check, no blob is used in that exposure; the last accepted measurement stays as an offset to the prediction. | "Never switch to a blob that failed the rule" (`docs/robot-interface.md`). Trying the next-nearest blob is how a robot ends up on the wrong bee. |
| D56 | 2026-11-13 | The cinema view is drawn on a 2D canvas by the simulator window and relayed as JPEG images over the simulator's WebSocket (path `/cinema`) to the control window. Blur is a soft disc edge, not a rendered depth of field. | It needs the truth, so it cannot come from the tracker. A 2D canvas needs no extra library and works in every browser; the picture only has to show whether the bee is framed and sharp. |
| D57 | 2026-11-13 | Mode switching by `state` (dead zone, focus rate) and a delay from stereo exposure to motor command are not emulated. The robot's control steps of a frame are computed at the start of that frame, so a `target` takes effect up to one frame (1/60 s) late. | Not needed for the Stage 5 criteria; the real values are unknown. Listed in `docs/robot-interface.md`. The extra frame stands in for the unknown processing delay of the real robot. |
| D59 | 2026-11-13 | The search window stays centred on the tracker's prediction, without the robot's own stereo correction. | The stereo correction comes from the blobs the window selects. Centring the window on it would let one wrong blob pull the window after it. The tracker's prediction is the anchor the robot cannot drag away. |
| D58 | 2026-11-13 | The robot only follows in real time; with `--fast` it holds position. | `target` travels over UDP in wall-clock time. Unpaced, the tracker falls behind in simulation time and its messages time out. Experiments without pacing are a Stage 7 topic. |
